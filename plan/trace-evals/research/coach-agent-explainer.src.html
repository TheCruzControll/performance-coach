Map

Six parts carry a message from the coach screen to Claude and back

A turn

A turn runs eight steps, and simple lookups skip the model

Data

The model sees your records only through the request, and stable parts go first

The model is Claude. Its lifting knowledge comes from Anthropic's pretraining. The repo adds no knowledge base, no retrieval and no fine-tuning.

Numbers never come from the model. e1RM, volume, load and trends come from src/lib/domain through analytics tools. The system prompt forbids the model from calculating any metric itself.

Memory

Memory is built from your records, not from old chats

What the coach always knows. Each segment opens with a snapshot: goals, the active program, the last 14 days planned against done, strength baselines, preferences, equipment and active injuries. It adds the last 28 days of pain reports, recovery notes and decided proposals, the 8 newest decisions with their reasons, and the 3 newest conversation summaries.

Old training: yes, by asking. get_training_history takes any start date, 28 days at a time. get_recent_workouts and get_exercise_history page backwards. get_personal_records returns the full PR timeline. With 8 model calls per turn, the coach can sample a period two years ago but cannot scan two years workout by workout.

Old chat: no. No tool searches past conversations. A long chat survives only as a summary note, and memory lists only the 3 newest. Something said in chat lasts only if it became a record, such as a stated dislike, a goal, or an accepted proposal.

Tools run three at a time, each with its own deadline. Zod checks the model's input before a tool runs. A failure goes back to the model as an is_error result such as INVALID_INPUT or TIMEOUT. The owner id comes from the server, so the model cannot choose whose data a tool reads.

Why

Testing without an API key shaped most of the design

Choice Reason on record Evidence
A hand-written loop The SDK's Tool Runner runs on the SDK client, so the mock could not drive the same loop. stated ADR 0013
A mock that rejects bad requests No key in development or CI. A bad request would otherwise fail only in production. stated ADR 0009, b841ff52
Tools, not pasted history Replayed history is "costly, drifts from the records, and replays any injected instruction". stated ADR 0014
Stable bytes first Keeps the cached part of the prompt identical across turns, and keeps stored text out of the system prompt. stated 8034793b
Proposals, not writes You accept every change to the program. stated ADR 0014
Loop and mock are one decision The loop shape follows from needing the mock to drive it. inferred
Retry counts, 8 calls, token caps No written reason found. Code points to an "m5 plan" that is not in the repo. unknown

Every commit and ADR here was written by Claude and merged by you. The reasons above are the agent's framing, approved by the merge.

Tracing

Every step is already stored, but you can only see a list of runs

What exists. agent_model_calls stores each call's request id, stop reason, tokens, cost, time to first token and latency. agent_tool_calls stores each tool's input, output up to 16 KB, status, duration and any proposal it created. Policy interventions are stored there too, named _policy. Deletes are refused by the database.

No outside platform is installed. package.json has no OpenTelemetry, Sentry or Langfuse. ADR 0007 kept observability in Postgres and deferred OpenTelemetry to the coach milestone.

The plan you picked, own tables plus a page:

  1. getRunTrace(ownerId, runId) in services/coach/runs.ts groups a run's calls, tools and messages by call_index.
  2. GET /api/coach/runs/[run] with the same owner-only and rate-limit guards as the list.
  3. A page at /coach/runs/[run], opened from each row of the usage sheet: one card per model call, its tools nested and collapsed.
  4. A mock-provider service test and a Playwright test that opens a run.

No migration. Every column already exists.
