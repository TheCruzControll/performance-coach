# Queue

The work the build loop takes from. One row per slice. The `run-queue` skill
(`.claude/skills/run-queue/SKILL.md`) reads this file and keeps several rows moving at once, top
to bottom. Edit it by hand to add, reorder, or hold work.

This file is the plan, not the live state. While rows are in flight, their progress is on GitHub
(the pull request) and in the loop's git-ignored state file. The loop writes results back here in
a housekeeping pull request when it stops and after every ten merges.

Pull requests are written as `PR 499`, without a hash sign, so the docs checks that look for
merged-PR citations ignore this file.

## Status values

| Status       | Meaning                                                                    | Who acts  |
| ------------ | -------------------------------------------------------------------------- | --------- |
| `ready`      | Has a spec and its dependencies are merged. Not started.                   | the loop  |
| `needs-spec` | Named but not specified. The loop writes the spec first, then builds.      | the loop  |
| `pr-open`    | A pull request exists. The loop gets it green, verifies it, and merges it. | the loop  |
| `in-ci`      | The loop has reviewed it and pushed. CI is running, or a fix is in hand.   | the loop  |
| `parked`     | Two fix rounds failed, or it needs a decision. The note says why.          | the owner |
| `owner`      | Only the owner can do it (a device check, a secret, a sign-off).           | the owner |
| `hold`       | Skip until the owner removes the hold.                                     | the owner |
| `merged`     | Merged and the post-deploy checks passed.                                  | nobody    |

A row's `Depends on` lists row ids and open pull requests that must be `merged` first. An empty
cell means none.

### UI: Instrument v2

Instrument v2 is the next iteration of the Paper redesign. It replaces the Instrument design in
the section below for every screen. The owner's reason: the app, and the first Instrument design,
are too busy, with rows of buttons stacked on each other, boxed cells, a lot of text, and no room
for anything to breathe. v2 is the same product with less on each screen.

It is in the same Paper file, `Performance Coach — App flow`, on the page
`Instrument v2 · all screens`, as fifteen numbered artboards in one row: `1 · Get in`,
`2 · First run`, `3 · Today`, `4 · Train`, `5 · Workout`, `6 · Progress`,
`7 · Progress history, reviews and weight`, `8 · Coach`, `9 · Profile`, `10 · States`,
`11 · Desktop` to `14 · Desktop: coach, profile and states`, and `15 · Light theme`. Each phone
has a name and a one-line caption above it that says what changed or where a thing moved to. The
three unnumbered artboards above them (`1 · Waking up`, `2 · At the gym`,
`3 · Looking over the week`) are the first sketches; the numbered boards hold the same phones.

The rules the design follows. A spec and a review hold every screen to them:

- **One question per screen.** The answer is the biggest thing on it.
- **At most one filled button per screen.** Every other action is a plain row, a text link, or
  sits behind one `Change` or `More` entry that opens a sheet of plain sentences. No row of two or
  more buttons side by side.
- **No boxes.** No cards, bordered cells or stat grids. Space groups things first, then a hairline
  between list rows. A surface colour appears only for a sheet, a field, a chat bubble, a toast or
  a round control.
- **No mono type, no uppercase labels, no small label above a heading.**
- **Amber means the next thing to do, and nothing else.** Errors are one red line.
- **Four tabs with an icon and a label: Today, Train, Progress, Coach.** Profile is not a tab. It
  opens from the avatar at the top right of Today, and every Profile screen has a back link.
- **A chart is one series.** Each Progress view is a sentence that states the finding, one chart,
  and at most five rows.

How every row in this section is specified and built. The method of the section below still
holds: the spec comes from Paper, read through the Paper tools by the session that writes it;
Paper must be open on that file; values come from the nodes and never from a screenshot; the
`verify-coach` journeys must still pass; each row updates `docs/design-system.md` and `/design`;
the motion and performance budgets hold. What differs for v2:

- **A board's rows are layers named for what they hold** ("Sessions", "Sync and saving",
  "Security"). `get_children` on the artboard lists them; the specs below name them.
- **The nodes carry literal values.** The page uses no Paper tokens, and the file's token list is
  still stale. `v2/01` turns the values into tokens once; later rows use tokens.
- **The type is Mona Sans, with Hubot Sans for the one display line on a screen and Mona Sans for
  every large numeral.** PR 581 shipped Geist and lowercase mono labels from the first Instrument
  design. `v2/01` replaces both and records the change in `docs/decisions.md`.
- **These rows change what a screen contains and its wording, not only its look.** Where a phone
  shows less than the app does, the caption says where the rest went, and the row moves it there.
  A row never removes a capability the captions do not account for.
- **Sample content is invented.** Names, dates, weights and plan phases in the design are a story
  for the screens. The app's data and its real states are the truth.
- **A caption that ends `New in v2` marks something the app does not do today.** A screen row
  leaves it out unless `v2-decisions` says to build it.
- **Rows that change what the app records or asks wait for `v2-decisions`.** The row says which
  decision it needs.
- **Desktop and light are designed.** Each screen row covers the phone and its frame on boards 11
  to 14. Board 15 shows twelve screens in light; other screens derive their light values from the
  tokens `v2/01` sets, and the contrast checks and axe runs stay green.
- **Paper cannot set tabular numerals in these fonts** without slashing the zero, so the design
  has none. The app keeps `tabular-nums` wherever numbers line up.

`v2/04` to `v2/24` touch different screens and can run side by side once their dependencies are
merged. The rule against two rows changing the same files in the local stage applies.

### UI: the Paper redesign

**Superseded on 2026-11-22 by Instrument v2, the section above.** `ui/01` merged as PR 581. The
other rows are on `hold`, and PR 586 (`ui/02a`, the first design's buttons and chips) is open:
`v2/02` takes what still fits from it. The text below is kept for the method it describes, which the
v2 rows reuse.

The owner redesigned the app in Paper. The file is `Performance Coach — App flow`, and the page
`Instrument · all screens` holds ten artboards, one per area, each with numbered phone screens
labelled with their route. The page `Desktop` shows the same screens in a 1440 × 900 window: a left
rail instead of the tab bar, two columns where a phone has one, and sheets as centred dialogs. The
goal of these rows is that the shipped app matches those designs. They change how screens look
and are laid out. They do not change behaviour, data, routes or copy the design does not show.

These rows come first because later UI rows should be built on the new primitives. Between
`ui/01` and the last screen row, production shows new tokens on old layouts; that is expected.

How every row in this section is specified and built:

- **The spec comes from Paper, read through the Paper tools, by the session that writes it.** The
  `builder` agent has no Paper tools, so the spec must carry the exact values. Call `get_guide`
  with `paper-mcp-instructions` first, find the artboard and screen by name with `get_basic_info`
  and `get_tree_summary`, then read `get_jsx` (with `includeNodeIds: false`) and
  `get_computed_styles`. Never take a size or a colour from a screenshot; screenshots are only for
  checking the result.
- **Paper's token list is stale.** It still lists the lime accent and no mono font, but the
  screens use an amber accent, monospace lowercase labels, squarer corners and a text-only tab
  bar. The nodes are the truth, not the token list. `ui/01` settles the token values once; later
  rows use tokens and never hard-code a value.
- **Paper must be open on that file** for the tools to answer. If they do not, park the row with
  that reason. Do not build from memory or from a screenshot.
- **Each screen row covers the phone screen and its frame on the `Desktop` page.**
- **The design is dark only.** Keep the light theme working: `ui/01` derives light values for

## Lessons

What the loop has learned that should change how it works. One line each, newest first, with the
row that taught it. When the same lesson appears twice, the loop turns it into an edit to an agent
or skill file, in its own pull request, and removes the lines.

- A Svelte 5 component with a local named `state` makes `$state` parse as a store, and only svelte-check in CI sees it (PR 575). Before adding `$state` to an existing component, grep it for a local named `state`.
- A stack rebased after its base merged replays the base's old commit and conflicts. Rebase with `--onto origin/main <old base head>` so only the row's own commits move. (m7/51)
- A route budget can fail on a slice whose unit and integration checks all pass: the review page grew 1.9 KB past 60 KB (PR 578). A slice that adds a component to a page the load awaits should expect `pnpm budgets` to move. The limit is now 62 KB.
- `pnpm check:files` type-checks the files it is given and their imports, not the files that import them. m7r/31 widened `ProposalKind` and broke `apply/index.ts`, which no changed file imports. When a slice widens a union or a shared type, also pass its consumers (grep the type name). (m7r/31)
- A row built before an earlier row merged can fail types against the newer `main`: m7r/35 against the union PR 568 introduced. After rebasing onto a `main` that moved, run `pnpm check:files` on the changed files again before pushing. (m7r/35)
- A linear stack whose top pull request is green on the current `main` can merge as that pull request alone. Its CI already ran the exact tree a train would build; check with `git merge-tree` that `main` plus the top is the top. That saves a full CI cycle. (PR 565 to PR 567)
- A screen that shows a new kind of proposal must be checked from the owner's side, not only the service's: m7r/36's deload reached the review page as "Too late to change next week" with no way to accept it, a gap carried from the source commit. (m7r/36)
- The strict tool schemas share one budget of 24 optional parameters across every strict tool in a request (`STRICT_LIMITS` in `provider/validate.ts`). A slice that adds tool inputs states the new total in its spec. Reads are not strict and do not count. (m7r/23)
- A port from an old commit can bring back a bug `main` has since fixed: m7r/23 copied the filter that counted the Sunday before the week twice, which m7r/15 had fixed in `evaluate.ts`. The brief for a port lists the fixes `main` made since, to the code being ported. (m7r/23)
- An edit made after review still needs a type check when it changes control flow: moving a refusal up narrowed a union and failed `svelte-check` on PR 551. (m7r/26)
- A rebase that merges cleanly can still drop a line the stacked commit needs, and the tests may not notice. After restacking, diff the ported file against its source commit. (m7r/27)
- m7r/03 parked after two fix rounds. Its promise (no clash stands unexplained) held only because the repair dropped the previous week's planned load. Counting that load leaves residual-fatigue findings that one move cannot clear. It needs a redesign: a wider search, or a recorded kept finding. m7r/04 to m7r/10 wait on it. (m7r/03-generator-schedule)
- Golden hashes carried from an old branch fail on today's `main` for that reason alone. Regenerate them on a clean `main`, and check which values the old commit itself changed, before updating them. (m7r/01, m7r/02)
- Fixture Postgres URLs with a password fail the secrets scan (twice: PR 516, PR 521). `builder.md` now runs `pnpm security:scan` and builds fixture URLs from parts. (m9/27-runtime-role)
- The M7 stack (PR 416 onward) drifted about 490 commits behind `main`, and its base alone is 13k lines with a conflict. Re-slice it before the loop takes it. (m7-05-m7-stage-list)
- Light runs on `main` meant nothing tested `main`'s exact tree, and a Sunday-only failure sat there unseen: CI now runs `main` in full every night. (fix-progress-sunday-new-owner)
- A builder proving "fails without the change" used `git stash` and applied the owner's old stash into its worktree: the stash list is shared by every worktree. `builder.md` now forbids it. (m9/38-log-redaction)
- Squashing with `git reset --soft origin/main` after `main` moved folds a revert of everything `main` gained into the commit. Rebuild from the slice's own files and check `git diff --stat origin/main` before pushing. (m9/38-log-redaction)
- A perf fix that moves work out of the load window also moves it out of every check that measures that window. (m6-59-m6-perf, closed)
- A rebased pull request branch can only be pushed with `--force-with-lease`; `feature-slice` said never to force-push, which was meant for `main`. Fixed in the skill. (m5-61-docs-m5-status)
